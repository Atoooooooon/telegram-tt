# 客服 OnCall 场景与 Playbook 设计上下文

> 版本: v0.1
> 最后更新: 2026-06-06
> 状态: 场景记录与产品设计上下文

---

## 1. 工作台定位

客服工作台的目标不是做一个需要人工高度干预的大型坐席系统，而是做一个稳定、简洁、能辅助摸鱼的后台机器。

核心定位:

1. 管理有用消息，避免人工在多个 Telegram 会话之间反复切换查看。
2. 以 case 为单位聚合上下文，而不是只处理单条消息。
3. 帮助人工快速回复客户，并逐步接入 AI 自动回复。
4. 将机械化操作提炼成 playbook，由 AI 推荐或人工点击执行。
5. 成功 case 入库，后续用于提炼 skill，最终让 AI 逐步接管更多客服行为。

现阶段不追求全自动客服，而是:

1. AI 负责理解 case、推荐操作流程、生成回复草稿。
2. Playbook/规则引擎负责稳定执行确定性动作。
3. 高风险动作需要人工确认。
4. 人工保留最终判断权，复杂判断先不强行自动化。

## 2. 总体设计思路

### 2.1 从规则升级为 Case Playbook

旧规则主要面向单条消息，适合做过滤、转发、简单命令触发。

新的客服工作台应该以 case 为单位执行 playbook:

1. case 汇总同一问题相关的多条客户消息、图片、机器人回复和人工动作。
2. AI 根据 case 上下文识别意图，并在可用 playbook 中推荐一个。
3. 用户可以忽略 AI 推荐，手动点击任意可执行 playbook。
4. Playbook 内部继续复用现有 capability，例如:
   - `text_processor`
   - `check_message`
   - `wait_for_reply`
   - `switch_route`
   - `action_send_to`
   - `action_auto_reply`
   - `action_resolve_case`

### 2.1.1 引用消息上下文

客户经常不是重新发送完整信息，而是发一条补充消息并 reply 过去的订单消息。例如客户发资金流水视频，同时引用之前那笔代付订单。

case 上下文需要区分两层:

1. `caseText`: 当前 case 分组里的消息文本，保持原始边界。
2. `caseReplyText`: 当前 case 消息引用到的历史消息摘要，仅包含本地已加载到的 Telegram 消息。
3. `caseContextText`: `caseText + caseReplyText`，查单、跟进自动化、AI 推荐和订单号提取优先读取这个字段。
4. `caseContextMessages`: 当前 case 消息和已加载引用消息的去重集合，后续发送媒体、生成草稿、保存成功 case 都可以使用。

这个能力是加分项，不是强依赖。引用原消息没有加载到时，不阻塞 playbook，也不编造内容。

### 2.2 AI 与规则引擎的关系

推荐方向:

1. AI 在规则引擎前面，作为 case 意图识别、流程推荐、上下文总结能力。
2. 规则/playbook 负责执行稳定操作。
3. 规则中可以调用 AI，但应作为能力使用，而不是让 AI 自由执行所有动作。
4. 对外发送、上游反馈等高风险步骤必须支持确认。

也就是说:

```text
case 上下文 -> AI 识别意图/推荐 playbook -> playbook 编排 capability -> 需要时人工确认 -> 执行动作 -> 记录成功 case
```

### 2.3 自动执行与人工确认

执行策略应该写在 playbook JSON 的 step 上，而不是全局按 capability 固定。

原因:

1. 同一个能力在不同业务里风险不同。
2. 发送到内部群可能不需要确认。
3. 发送到上游群通常需要确认。
4. 辅助模式下可以只填入输入框/草稿，让手机端人工确认发送。

示例策略:

```json
{
  "executionPolicyByMode": {
    "oncall": "confirm",
    "assist": "auto"
  }
}
```

## 3. Case 生命周期

### 3.1 当前阶段状态

当前阶段主要维护:

1. 待处理
2. 处理中
3. 已回复
4. 已解决

已解决不应由 AI 默认判断，需要人工或明确规则动作标记。

### 3.2 已解决 case 入库

已解决 case 用于后续训练和 skill 提炼。

当前阶段入库来源:

1. 人工手动标记已解决。
2. AI/规则自动执行成功并触发 `action_resolve_case`。
3. 高风险动作被人工允许执行后，可记录为成功自动化案例。

当前不强求补全纯人工操作流程，因为人工在 Telegram 里的外部动作很难完整采集。

长期目标:

1. 优先记录全 AI/playbook/规则执行链路。
2. 从成功 case 中提炼可复用 skill。
3. 后续让消息保障也接入 AI，判断哪些 case 还没解决并提醒人工处理。

## 4. 场景一: 代收查单

代收查单是最常见场景。用户通常发送单号和图片凭证。

### 4.1 通用第一步

不应在用户刚发“图片 + 单号”时直接判断是 VA 还是 QRIS。

正确流程:

1. 从 case 中提取用户给的单号。
2. 在客户群回复或发送:

```text
/ds ${单号}
```

3. 等待机器人回复。
4. 根据 `/ds` 机器人回复判断订单状态和支付方式。

### 4.2 `/ds` 成功

如果 `/ds` 返回订单状态成功，说明订单本身已成功。

处理策略:

1. 不需要继续查。
2. 可通过规则标记 case 已解决。
3. 不应因为没有匹配“处理中”就把流程当失败。

典型返回:

```text
商户: WMXa4n
流水号: 9be23b356c134dc8994709a660560029
状态: 成功
订单金额: 10,000
实收金额: 10,000
明细:
   编号: 9be23b356c134dc8994709a660560029
   付款方式: DANA
   VA/URL: https://m.dana.id/s/qpp2xjaq
   实收金额: 10,000
   交易时间: 2026-06-05 14:40:51
   到账时间: 2026-06-05 14:51:56
```

### 4.3 VA 处理中

如果 `/ds` 返回:

1. 状态为处理中。
2. `VA/URL` 是数字 VA。

则按 VA 查单流程处理。

典型返回:

```text
商户: hxl1Yn
流水号: PAYIN8751029246519222272
状态: 处理中
订单金额: 1,700,000
实收金额: 0
明细:
   编号: PAYIN8751029246519222272
   付款方式: BRI
   VA/URL: 1604018171991899
   实收金额: 0
   交易时间: 2026-06-05 07:09:31
   到账时间: null
```

处理流程:

1. 回复客户:

```text
稍等，我们反馈核实一下。
```

2. 去技术群发送:

```text
/polist msn${单号}
```

3. 等待技术群机器人回复。
4. 从回复里提取供应商。
5. 根据供应商通过 `switch_route` 设置 `targetChatId`。
6. 准备发送到对应上游群:

```text
/fs pls check va ${va}
```

7. 最后一步需要人工确认。

重要要求:

1. 图片和文字要作为一条消息发给上游，避免拆成两条导致上游机器人漏处理图片。
2. 不应抽象出业务专属能力如 `action_prepare_upstream_feedback`。
3. 应扩展通用发送能力，让 `action_send_to` 支持 media source、caption、draft 等通用场景。

### 4.4 供应商到上游群映射

供应商路由应该通过 `switch_route` 设置变量，而不是新增业务能力。

示例:

```json
{
  "id": "route_supplier_upstream_group",
  "capabilityId": "switch_route",
  "config": {
    "inputField": "supplierName",
    "defaultMode": "regex",
    "mergeData": true,
    "casesJson": "[{\"match\":\"PakaiLinkKILAUSAFIR-PAKAILINK\\\\(153\\\\)\",\"gotoStep\":\"prepare_upstream_feedback\",\"data\":{\"targetChatId\":\"-5213573223\"}}]"
  }
}
```

说明:

1. `match` 支持 regex。
2. 如果只写 `BNC_TEST-BNC`，在 `contains` 或 `regex` 模式下都可以匹配 `BNC_TEST-BNC(14)`。
3. 下游发送步骤读取 `{{targetChatId}}`。

### 4.5 QRIS 处理中

QRIS 比 VA 更复杂，因为需要看图片凭证:

1. 判断凭证是不是我们的。
2. 识别凭证里的商户名。
3. 识别是否有 RRN。
4. 使用 RRN 去技术群查:

```text
/polist msn${rrn}
```

5. 如果查到绑定订单:
   - 如果是当前商户，说明用户给错单号，告诉用户对应单号。
   - 如果是其他商户，告诉用户这是其他商户的凭证。
6. 如果没有相关订单，回复用户:

```text
这笔目前未收到资金，有变动立即同步。
```

当前阶段暂不优先做完整 QRIS 自动化，因为 OCR/RRN/凭证商户识别还没稳定接入。

## 5. 场景二: 代付未到账

用户反馈某个代付单号没收到钱。常见输入是单号加资金流水视频。

### 5.1 初始查询

先在客户群执行:

```text
/df ${单号}
```

### 5.2 `/df` 成功

如果订单状态成功，回复用户提供资金流水:

```text
请提供一下从创建订单到目前的资金流水，我们反馈核查。
```

随后先执行 `/dolist msn{orderNumber}` 获取 `ssn` 和供应商信息，并通过 `switch_route` 得到实际上游群。然后进入 `suspend_for_human` 人工确认门:

1. 后端在 Redis 中创建 pending gate。
2. 后端通过 Telegram bot 向“设置 -> 自动化 -> 远程确认群”发送确认消息；该确认群支持选择 forum 话题。
3. 确认消息会打印订单、`/df` 返回、`/dolist` 返回、`ssn`、供应商、命中的上游别名、目标上游群和准备填入的 `/fs` 草稿。
4. 人工在手机或其他设备上检查客户视频后，reply 这条 bot 消息:
   - `1` / `OK` / `确认` / `继续`: 继续后续 playbook。
   - 任意其他非空文本: 停止后续 playbook。
5. 这个 gate 的状态存在 Redis 中，不依赖 Web 页面内存。
6. gate 有超时；超时只会让本次等待过期，不会自动发送上游消息。过期或已完成记录会按保留期清理。

说明:

1. `wait_for_reply` 继续用于 `/df`、`/dolist` 这种短时间机器人回复。
2. 人工视频核对可能等待几分钟甚至更久，建议使用 `suspend_for_human`；不用它时仍可完全人工处理。
3. 后端只负责可靠保存确认状态和接收确认群 reply；继续生成草稿仍由 Web/Electron 执行。

### 5.3 视频核对

人工主要判断:

1. 视频里的 App 是否与订单付款方式一致。
   - 例如订单是 OVO，用户发 GoPay 视频，就是不对。
   - 例如订单是 OVO，视频中是 DANA，也不对。
2. 视频里的收款账号是否和订单账号一致。
3. 视频覆盖时间是否从创建订单到当前。
4. 当天流水里是否已经收到钱，避免用户漏看。

如果视频 App 不对应，回复用户提供正确流水视频。

### 5.4 反馈上游

如果视频核对通过并且 `suspend_for_human` 收到确认:

1. 已在人工确认前去技术群发送:

```text
/dolist msn${单号}
```

2. 从返回信息中获取上游、上游订单号 `ssn`。
3. 已根据上游或供应商字段通过 `switch_route` 设置 `targetChatId`。
4. 确认通过后，在对应上游群填入草稿:

```text
/fs ${ssn} user report no funds received.
```

注意:

1. 不自动发送到上游，只填入草稿并打开目标群，人工确认后发送。
2. 当前 Web draft 能力主要写文本草稿，视频无法保证自动进入草稿；若客户视频是在 suspend 后才补发，人工需要把视频一起补到上游消息。
3. 后续可以优化为恢复执行前刷新 case media，或者增加明确的“选择客户视频并发送/草稿”能力。

这个场景中的视频判断较复杂，当前阶段先把机械步骤自动化，复杂判断交给人。

## 6. 场景三: 服务不稳定与报警

报警群会出现机器人报警消息。

人工处理逻辑:

1. 如果短时间多次报警，要留意报警内容。
2. 看报警涉及哪个账号和渠道。
3. 去技术群测试账号/渠道，例如:

```text
/scheck sa143 methodsqris
```

4. 根据测试结果判断:
   - 是否能正常生成 VA/QRIS。
   - 是否付款失败。
   - 是否需要自己用手机扫码测试。
5. 如果确认有问题，反馈上游让他们检查。

这个场景适合作为后续主动 playbook:

1. 自动聚合短时间报警。
2. 推荐或执行 `/scheck`。
3. 把测试结果作为 case 上下文交给 AI 总结。
4. 高风险上游反馈仍需人工确认。

## 7. 场景四: 卡单统计与催上游

人工会不定期在技术群执行:

```text
/dpgroup
```

机器人返回卡单统计，例如:

```text
当前卡单统计:
卡单数量: 56
账户: AgungSubsidiary-子账户4-APS--DURIAN_PAY(160)
银行: BRI
金额: 12,387,811
数量: 37
```

如果某个账户卡单较多，继续查该账户:

```text
/dplist sa160 ssn
```

返回示例:

```text
please check processing disburse orders:
2062082936026587137 => dis_item_2dSw4RofPj8875
2062083961353568257 => dis_item_ZNXbsCda6Z4089
```

处理:

1. 根据账户编号或供应商映射到上游群。
2. 把 `please check processing disburse orders` 后面的内容发给上游。
3. 用于催促上游处理卡单。

这个场景很适合无消息时主动执行 playbook。

## 8. 场景五: 机器人投诉/通知转发

已有规则中存在简单但实用的前置过滤和转发逻辑。

### 8.1 投诉消息转运营投诉群

典型逻辑:

1. 监听指定上游群。
2. 只处理指定机器人发送者。
3. 文本 normalize。
4. 匹配关键词:

```text
complaint|chargeback|dispute|投诉|客诉|拒付|争议|申诉
```

5. 转发到运营投诉群。
6. 发送来源群和 @ 人提醒。

### 8.2 通知维护转内部群

典型逻辑:

1. 监听指定群和机器人发送者。
2. normalize 文本。
3. 匹配关键词:

```text
notice|alert|maintain|maintenance|通知|公告|维护|升级|故障|恢复
```

4. 发送内部命令:

```text
/maintain 群组名:{{chatTitle}} 通知内容:[{{text}}]
```

这类规则仍适合保留在旧规则系统中，不一定需要升级成 case playbook。

## 9. 场景六: 对接问题与其他咨询

新商户对接、参数问题、业务咨询等情况很多，不适合一开始做成强规则。

当前策略:

1. 由 AI 生成摘要和回复草稿。
2. 人工判断。
3. 后续从成功 case 中提炼高频 skill。
4. 等稳定后再形成 playbook。

## 10. AI 推荐 Playbook 的原则

AI 推荐只能从可用 playbook 中选择一个。

推荐阶段不应该做的事:

1. 不应根据用户刚发的“图片 + 单号”猜 VA/QRIS。
2. 不应编造不存在的 playbook。
3. 不应直接决定 case 已解决。
4. 不应绕过需要确认的高风险步骤。

推荐阶段应该做的事:

1. 根据 case 文本、图片摘要、历史消息和已知字段判断意图。
2. 选择最合适的 playbook。
3. 给出简短理由。
4. 如果信息不足，仍可推荐先查询再分支的通用流程。

---

## 11. OCR 与多模态扩展方向

后续查单会涉及图片识别。

可选方向:

1. 在 playbook 中调用外部 OCR/API 工作流，例如已有 Coze 凭证识别工作流。
2. 在 `text_processor` 的 extract 能力中增加 AI/OCR 提取模式。
3. 使用多模态 AI 识别凭证内容，再把结果写入 pipelineData。

倾向:

1. 具体抽取能力放进 `text_processor` 更合理。
2. 更抽象的能力才单独做 AI capability，例如 case 意图识别、playbook 推荐。
3. OCR 结果应该进入 case 上下文，供后续 AI/规则继续判断。

---

## 12. UI 设计原则

工作台应保持简约:

1. 不做复杂的大型操作台。
2. 不展示过多固定信息流转。
3. 重点展示:
   - case 摘要
   - 自动读取上下文
   - AI 推荐/可手动执行 playbook
   - 执行线
   - 回复输入框
4. 执行线用于展示 AI 推演出来的操作和 playbook 真实执行步骤。
5. 失败步骤 hover 应能看到调试参数，方便定位 JSON 配置问题。

无消息时:

1. 展示主动执行 playbook 页面。
2. 可用于卡单统计、巡检、催上游等无需客户消息触发的任务。

---

## 13. 当前阶段优先级

第一阶段重点:

1. UI 简洁稳定。
2. 外部 AI 配置可用，支持多 AI profile。
3. Case playbook 可被 AI 推荐，也可人工手动执行。
4. VA 查单 demo 能跑通真实流程。
5. `wait_for_reply` 能正确等待机器人 reply。
6. `suspend_for_human` 能把长时间人工确认放到后端 Redis，并支持手机 reply 控制群确认。
7. 高风险步骤支持人工确认。
8. 成功 case 能入库。

暂缓:

1. 完整 QRIS OCR 自动化。
2. 视频流水自动判断。
3. 纯人工流程补录。
4. 全自动接管所有客服行为。
5. 可视化 playbook 编辑器。

---

## 14. 长期目标

长期目标是逐步养成一个全能客服机器人:

1. 先用 playbook 固化简单机械流程。
2. 成功 case 入库。
3. 从成功 case 中提炼 skill。
4. Skill 以 Markdown 或结构化文档沉淀。
5. AI 读取 case 上下文和 skill，生成可执行计划。
6. 高风险动作由人工确认。
7. 稳定后逐步放开自动执行权限。

最终状态:

```text
AI 理解 case -> 读取 skill -> 选择/生成操作计划 -> 调用 playbook/规则能力 -> 必要时确认 -> 回复客户 -> 成功样本沉淀
```
